## Overview

Strategic plan for maturing nodus from an in-tree vendored crate to an independently extractable, production-ready workflow-language library. The arc runs: spec completeness → library hardening → extraction readiness → observability & extension framework → portability → testing → capability manifest (LP-8). Each new contract spec is implemented, then its L2 spec is synced to the realized Rust shape.

Execution mode: **Sequential** (spec correctness must precede hardening; hardening must precede extraction).

## Phase 35 — Output Validators (l2-nodus-commands §4.5) — Planned

*Evaluate the `^validator`s the language has always accepted and never judged. Decomposed into tasks on entry.*

A rule is an output rule on the command that carries it, judged after the answer and before the value is bound. Three rules are the core's because their meaning is fixed by the value alone (`len`, `min_len`, `required`, evaluated by the executor and not overridable); every other rule is the provider's, through the provider trait's `validate` member, which lands here with its first caller. Four verdicts — `Pass`, `Assumed`, `Fail`, `Unavailable` — where a rule nobody can evaluate fails closed. `VALIDATE` gets its real result and `VALIDATE_NO_RULES`; the `WITHOUT` clause reads the commands that completed cleanly, so a `VALIDATE` whose rule failed no longer unlocks a `PUBLISH`; `NODUS:VALIDATION_FAILED` gains its first emitter; and an `Assumed` verdict raises `VALIDATOR_ASSUMED:<rule>` and joins the mode decision Phase 34 wrote.

> **Ordering is load-bearing.** The core rules and the failure path land before the provider hook, because a rule that fails must be a typed, `Signal`-free failure before any host can be asked about one. The `WITHOUT` change comes last: it alters what an existing rule check reads, so it needs the `VALIDATE` result it depends on. Waits on Phase 34 for the provider trait, the answered-value binding point and the mode decision.

## Phase 36 — Effect Identity, Command-Scoped Retry & the Command Record (l2-nodus-commands §4.6 · §4.7 · §4.9) — Planned

*Make a retried step stop re-committing what already completed, and give a provider the identity it needs to keep an effect at-most-once. Decomposed into tasks on entry.*

The effect key (run, versioned digest, restart count, step, structural position, loop iterations, namespace) and `attempt` join the request, and `world()` joins the trait, each with its call site. The key is derived from the AST alone, so a whitespace edit changes nothing. Within one `~RETRY` step the executor keeps a commit memo: a command that completed cleanly is not executed again — its value is re-bound and re-recorded, with no rule check, gate, provider call or event — and only the command that failed and those after it run again, with the same key and `attempt` + 1. `EventAnnotations::command` carries the command record (provenance, key, attempt, world) on the `StepEnd`, and a `SETTLE` inside a retried step never settles twice. Closes the multi-command case `l2-nodus-control-flow` §4.4 recorded and gives resume-by-replay the identity DG-4 lacked.

> **Ordering is load-bearing.** The key and its stability properties land before the memo, because the memo is keyed by it and a memo over an unstable key would silently re-execute. The record comes last: it reports what the key and the memo did. Waits on Phase 34 for the executor's answer path, and on Phase 35 only for the record's `Assumed` case; the existing retry tests review as a group before the memo lands.
