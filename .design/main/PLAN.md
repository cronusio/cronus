## Phase 27 — Invocable Registry & CLI Derivation (`crates/contract` · `crates/domain` · `crates/core` · `crates/cli`) — Done

*Realizes `l2-invocable-registry` (1.1.0) and `l2-surface-conformance` (1.0.1), and carries `l2-cli` 1.2.0 onto them under the entry contract of `l1-launch-handoff` (1.0.0). The first phase since Phase 13 that is **structural before it is behavioural**: it mints one primitive and moves the first consumer onto it, changing what a user can observe as little as possible.*

**The specification moved under this phase mid-flight, and the plan says so rather than absorbing it quietly.** Tracks A and B shipped against `l2-invocable-registry` 1.0.0. A study of how comparable products organize a command surface then produced a spec wave that **refuted the assumption underneath track D** — that the command line's verb set and the interactive surface's verb set are one set — and closed six gaps between the registry spec and its own L1 parents. Two consequences are planned explicitly. A **retrofit** (T-27A04, T-27B05, T-27B06) brings the shipped tracks up to 1.1.0; it sits on the critical path because both the corpus and the generated parser depend on its shape. And **T-27D01 is renarrowed**: it generates the *semantic* half of the command line only, with the installation half declared in the frontend's own closed grammar (T-27D01.1). Generating all of it was the 1.1.0 reading and does not survive the launcher contract — an installation verb must be answerable when the composition it would configure is precisely what failed to come up (LH-1/LH-5).

**Why this phase exists.** A code-first audit of the three frontends found one mapping written by hand three times — a build-time command enum (29 groups), a separately maintained slash catalog (21 verbs), and a per-capability IPC handler list (4 commands) — each internally consistent and mutually divergent, with a fourth copy forming in the desktop's TypeScript client. No import gate, type check, or per-surface test can see that class, and the one check that claimed to (the terminal UI's parity assertion) was comparing a hand-copied constant against itself and passing while the surfaces differed by eight verbs.

**The constraint that settled the architecture is mechanical, not stylistic.** Every one of those surfaces is compile-time bound. An extension the user installs after the build has nowhere to attach a verb, whatever its manifest declares — and extension manifests already carry a capability list no code consumes. The plugin requirement therefore forecloses the cheap options before cost enters the discussion, which is why the spec layer's answer (SP-11's catalog, EP-2's `contribute` seam, EP-12's single registration door) is adopted rather than a lighter local one.

**Ordering is a spec obligation, not a preference.** SP-9 requires the shared primitive to exist *before* the second implementation, because after both exist someone must decide which was right and stage a behaviour change. Hence: primitive, then first consumer, then the corpus that pins them — with Phases 28 and 29 adding consumers to a registry that is already proven.

**Behaviour-preservation is the phase's acceptance property (SP-10).** Migrating a verb onto the registry must not change what it does in the same commit. Four known-wrong behaviours the audit surfaced — a store failure reported as an empty result with a success code, an output-format flag discarded in nine sites, structured output assembled by unescaped string formatting in five, and a redaction path fed an empty secret list on every surface — are recorded as **residuals at their owning invocables**, correction deliberately deferred rather than folded into this migration. Two of them are correctness defects, and shipping them one release longer is the deliberate cost of a diff a reviewer can actually read. **`[CORRECTED]`** The original plan for this phase named Phase 29 as where they would be corrected; grounding at that phase's own planning time found none of the four actually reachable from its subsystem (three are core-tier or CLI-only, one needs a project-wide primitive that does not exist yet) — all four remain open residuals, recorded in `l2-surface-conformance.md` §4.7/accepted-debt, owned by whichever later phase actually touches their real sites.

## Phase 31 — Discovery Classification (`crates/simulation`) — Done

*Closes `l2-simulation-suite` §3's one standing **Pending** row — USM-13, carried since the harness shipped, whose own text names this planning pass as its reconciliation point.*

The harness records discoveries as free text. `RunState.notes` is a `Vec<String>`, `cronus-sim note` joins its trailing arguments into one string, and the report renders that string back. USM-13 says a discovery **may** carry a class from the improvement-loop taxonomy and **may** carry a proposed remedy; neither has anywhere to live, so both are lost when the run ends and survive only as prose someone re-reads. Two of this project's own early scenario runs surfaced exactly that: genuine friction, recorded as an unstructured `note`, distinguishable from a defect only by reading it.

This phase adds two optional fields to a record. A classified discovery still cannot fail a run (USM-3), a proposed remedy is still a claim for a human to weigh, and the run still repairs nothing (USM-12). An implementation that reads a `defect` class and acts on it has built a different phase.
